# StudyFlow — AI Study Assistant

**Live Demo:** https://ai-study-assistant-client-five.vercel.app/  
**Screen Recording:** https://drive.google.com/file/d/1O6PgKViYLMqLAAuQX_iSQ_Tx7r79szoC/view?usp=sharing

Paste a topic or your own notes, and StudyFlow turns them into a set of interactive
flashcards and a multiple-choice quiz — generated by an LLM, validated on the way in,
and rendered as real UI components. Not a chatbot: the model never gets to print
raw text at you, it only ever gets to fill in a strict schema.

## Features

- Free-form topic/notes input, with example topics to try
- AI-generated flashcards (flip to reveal answer, previous/next, progress indicator)
- AI-generated multiple-choice quiz (one question at a time, immediate feedback,
  explanations, final score)
- **Retry Wrong Answers** — after finishing the quiz, retake only the questions
  you missed, as many times as you like
- Explicit loading, error, empty, and success states — the UI is never blank
  or broken, even when the AI misbehaves
- Stale-response protection — an old request can never overwrite a newer one
- Fully responsive, from mobile up to desktop
- No API key in the browser — all Gemini calls happen server-side

## Tech Stack

**Frontend:** React 18 (hooks, functional components), Vite, Tailwind CSS
**Backend:** Node.js, Express
**AI:** Google Gemini (`gemini-2.5-flash`, via the official `@google/genai` SDK)

## Architecture

```
User types a topic/notes
        │
        ▼
React frontend (client/)
        │  POST /api/study/generate  { input }
        ▼
Express backend (server/)
        │  builds a prompt + JSON schema
        ▼
Gemini API  (responseSchema constrains the output shape)
        │  raw JSON (untrusted)
        ▼
Server-side validation (server/utils/validateStudyData.js)
        │  only valid, well-typed data passes through
        ▼
{ success: true, data } or { success: false, error, code }
        │
        ▼
React state (App.jsx)
        │  client-side validation again (defense in depth)
        ▼
Interactive flashcards + quiz components
```

The frontend never talks to Gemini directly. It only ever talks to our own
Express API, which is the only place the Gemini API key exists.

1. Go to [aistudio.google.com/app/apikey](https://aistudio.google.com/app/apikey)

## How It Works

1. The user types a topic or pastes notes into the textarea and clicks
   **Generate study set**.
2. The frontend sends `POST /api/study/generate` with `{ input }`.
3. The backend builds a prompt instructing Gemini to return **only** JSON
   matching a fixed schema, and passes that schema to Gemini's
   `responseSchema` config — this constrains the model's output at the
   token level, not just via instructions in the prompt.
4. The backend parses the response and runs it through
   `validateStudyData()`, which checks every field, type, and array shape
   before anything is trusted (see [Failure Handling](#failure-handling)).
5. Only validated data is sent back to the frontend as
   `{ success: true, data }`. Anything invalid becomes
   `{ success: false, error, code }` instead — the server never forwards
   broken data hoping the frontend will cope with it.
6. The frontend re-validates the data once more (`utils/validation.js`) before
   putting it in state, purely as a second, independent safety net.
7. Validated data becomes flashcards and a quiz, both fully interactive,
   fully local React state — no further network calls needed.

## Failure Handling

This was the main point of the assignment, so here's each case and where it's handled:

| Case | Where | Behavior |
|---|---|---|
| Empty input | `App.jsx` (before any request is sent) | Inline message, no API call made |
| Slow API | `LoadingState.jsx` | Spinner + "Creating your study set…"; Generate button/form is unmounted so no duplicate submits are possible while loading |
| Network/API failure | `api.js` throws → `App.jsx` catch → `ErrorState.jsx` | "Something went wrong…" + Try Again |
| Malformed JSON from Gemini | `gemini.service.js` catches `JSON.parse` failure, tags it `MALFORMED_JSON` | Controller returns a friendly 502; frontend shows the same error state |
| Wrong JSON shape (missing fields, wrong types, bad `correctAnswer` index, etc.) | `validateStudyData.js` | Rejected before ever reaching the client; friendly error, retry available |
| Empty AI response (0 flashcards/quiz questions) | `validateStudyData.js` distinguishes this from a generic shape error via the `EMPTY_RESULT` code | Frontend shows a distinct `EmptyState.jsx`, not the same as a hard error |
| Stale responses | `App.jsx`, request-ID counter | See below |

### Why request IDs instead of AbortController

The assignment suggests either approach. I went with a simple incrementing
request ID (`latestRequestId` in `App.jsx`) instead of `AbortController`:

- Every call to `handleGenerate` grabs `const requestId = ++latestRequestId.current`.
- When the response comes back (success *or* failure), we compare that captured
  `requestId` against `latestRequestId.current`. If a newer request has started
  in the meantime, the result is silently discarded — it can never call `setState`.
- This is correct regardless of network timing: it doesn't matter whether the
  first request finishes first or second, only the *last one fired* is ever
  allowed to update the screen.

I chose this over `AbortController` because it needs no `signal` plumbing
through `fetch`, no `AbortError` special-casing, and the in-flight request
finishing "for nothing" is a harmless, negligible cost at this app's scale.
It's also easier to reason about and explain: one counter, one comparison,
no cancellation lifecycle to get wrong.

## Known Limitations

- No streaming — the full study set is generated before anything renders.
  For a set this size, generation is fast enough that a spinner is an
  acceptable trade-off, but streaming would improve perceived latency.
- No persistence — refreshing the page loses the current study set. There's
  no backend storage or localStorage session save (this was left as a
  stretch feature per the brief).
- Quiz retry state lives only in memory for the current session — closing
  the tab loses your retry history.
- Gemini occasionally produces flashcards/quiz questions that are a little
  generic for very short or vague inputs (e.g. a single word); the app
  handles this gracefully (it's still valid, structured output) but the
  *content quality* in that case depends on the model, not the validation layer.
- No automated test suite (unit/e2e) — testing was manual, per the assignment's
  suggested scope for an ~8-hour project.

## Future Improvements

- Stream the AI response so flashcards can start appearing before the whole
  set finishes generating
- Save/reload a session via `localStorage` so a refresh doesn't lose progress
- A refinement loop — "make these questions harder" as a follow-up prompt
  that edits the existing set instead of regenerating from scratch
- Dark mode
- Let the AI return different block types (e.g. a diagram or checklist) for
  topics that aren't well suited to pure flashcards/quiz
